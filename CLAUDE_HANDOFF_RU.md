## 1. Что это за проект

Minecraft Bedrock-мод (behavior pack + resource pack) **Growing Villages**:
растущая ванильная деревня вокруг предмета «Колокол-Оракул». Только
ванильные блоки/текстуры/модели. Деревня растёт по **20 уровням** —
контентно это ПОЛНАЯ, законченная линейка (L1–L20), дальше по плану уровней
нет (см. §6 «Неизменяемые инварианты»).

Работай с приложенным source ZIP (см. имя файла в комплекте передачи — оно
всегда содержит `bugfix_round3b` или новее). Это единственная одобренная
база на момент передачи.

### Архитектурный принцип L16-20 (важно понимать перед правками)

```
ui.js -> extension_runtime_16_18.js -> progression_16_20.js  (чистое решение)
                                     -> planned_build_transaction.js (физика)
      -> final_runtime_19_20.js     -> (те же planner+dispatcher)
```

`ui.js` никогда не импортирует `progression_16_20.js` или
`planned_build_transaction.js` напрямую — только через один из двух
координаторов. Координаторы L16-18 и L19-20 никогда не импортируют друг
друга. Проверяется автотестами (`extension_runtime_16_18.mjs`,
`final_runtime_19_20.mjs`, секция «module ownership boundaries»).

**Двухфазный принцип на L16-20** (не нарушай при правках): шаг арки/депозит
(Фаза A) тратит ресурсы игрока и двигает state; сам build (Фаза B) не тратит
НИЧЕГО — так провалившаяся физическая постройка не может стоить игроку
ресурсов или уровня.

## 5. История багфиксов (root cause + фикс, кратко; полные версии — в
   соответствующих `BUGFIX_ROUND*_REPORT_RU.md`)

Все баги ниже найдены **вживую на iPhone владельца**, не автотестами — мок
долго не ловил нативные type-ошибки и geometry-баги Bedrock. Методология
на каждый раз одна и та же: сначала root cause в реальном коде (не
догадка), потом минимальный фикс, потом тест, который **доказывает
причинность** (там где возможно — падает на старом коде/логике, проходит
на новом), потом полный regression с точными цифрами.

### Round 1 (см. `BUGFIX_ROUND1_REPORT_RU.md`)
1. Стена ратуши срезалась при level-up (полоса выравнивания дороги
   слишком широкая).
2. Меню ремесленников не открывалось (`RawMessage.with` — массив объектов
   вместо массива строк).
3. Ошибка редкого автоспавна деревни (`getEntities()` без `y`).
4. Watchdog-краш на укреплениях (синхронная зачистка ~9000 колонок) —
   вынесена в фоновую задачу через `system.runJob`.

### Round 2 (см. `BUGFIX_ROUND2_REPORT_RU.md`)
1. `minecraft:cobblestone_stairs` — несуществующий id (правильно —
   `minecraft:stone_stairs`), дырявая крыша шахтёра.
2. Фонарь в стене ратуши/любого дома — решётка фонарей `extendPath` не
   знала о занятых участках. Фикс: `protectedRects` параметр + новый
   `builtPlotFootprints()` в `levels.js`.
3. Пол дома кузнеца/шахтёра становился травой при повторном укреплении
   стен (L5→L8→L10 пересвипает один и тот же интерьер каждый раз) — тот
   же `protectedRects`, теперь и в `terrain.js`/`walls.js`.
4. Домик алхимика/старожилы висел в воздухе — `specials.js` никогда не
   выравнивал площадку (`prepareSite`) перед постройкой, в отличие от
   всех остальных зданий. Исправлено.
5. **§5.5 Углы стен/удалённые постройки** — первая попытка через
   `/tickingarea add`. Оказалась неполной, см. Round 3.

### Round 3 (см. `BUGFIX_ROUND3_REPORT_RU.md`)

### 5.5 Углы стен всё ещё не достраивались — правильный фикс

`/tickingarea add` **не подгружает чанки синхронно** — только
регистрирует область, сами чанки стримятся в течение следующих нескольких
тиков (официальная документация Microsoft). Спавн стражи/голема/жителя
шёл сразу после регистрации, в том же синхронном вызове — чанк ещё не
успевал подгрузиться, особенно на 40-60+ блоках от игрока.

**Фикс:** `withRetry()` в `terrain.js` — первая попытка сразу, при ошибке
(в т.ч. `LocationInUnloadedChunkError`) — повтор через `system.runTimeout`
(40, 100, 200 тиков), пока `/tickingarea` не подгрузит область. Подключено
к спавну стражи башен, големов ворот, ремесленников, жителей в
`village.js` — весь блок "заспавнить + повесить теги" ретраится атомарно.

**Важно, не решено полностью:** это чинит только СПАВН СУЩНОСТЕЙ. Кладка
БЛОКОВ (сама стена, дома) всё ещё не имеет гарантии на действительно
холодных (никогда не посещённых) чанках — `setBlock`/`setType` молча
глотают ошибку (см. `util.js`), просто теперь у них больше шансов успеть,
потому что `withLoadedArea` регистрирует область заранее, а сама
синхронная кладка занимает реальное время выполнения. Если владелец снова
пришлёт скриншот именно с недостроенными БЛОКАМИ (не с ошибкой спавна в
логе) — это следующий кандидат на починку, и потребуется другой механизм
(ретраить конкретные блоки или очередь недостроенных фрагментов, не всю
постройку разом).

### 5.6 Староста не открывал меню — паттерн спавна взрослого жителя

`minecraft:villager_v2` при обычном спавне имеет шанс родиться ребёнком
(как у коровы) — ребёнок не открывает меню/торговлю так же, как взрослый.

**ВАЖНО — это единственное место, где Round 3 сам внёс регрессию (Round
3b, хотфикс), прочитай внимательно, если трогаешь спавн жителей:**

- ❌ **НЕ ИСПОЛЬЗУЙ**: `dimension.spawnEntity("minecraft:villager_v2<minecraft:ageable_grow_up>", loc)`
  — этот синтаксис (spawn-событие внутри строки идентификатора) **устарел
  начиная с движка 1.21.80** и теперь выбрасывает
  `InvalidArgumentError` на КАЖДЫЙ спавн. Именно это сломало закладку
  деревни целиком в 0.5.2 (Round 3) — исправлено в 0.5.3 (Round 3b).
- ✅ **ПРАВИЛЬНО**: `dimension.spawnEntity(VILLAGER_TYPE, loc, ADULT_SPAWN_OPTIONS)`
  — два отдельных экспорта из `util.js`: `VILLAGER_TYPE =
  "minecraft:villager_v2"`, `ADULT_SPAWN_OPTIONS = { spawnEvent:
  "minecraft:ageable_grow_up" }`, передаются как 2-й и 3-й аргумент
  `spawnEntity`, никогда не объединяются в одну строку.
- Мок в `tests/node_modules/@minecraft/server/index.js` **теперь сам
  выбрасывает ошибку**, если где-то встретит `<` в идентификаторе при
  спавне — эта конкретная регрессия физически не может повториться
  незамеченной, тест упадёт сразу.
- Заодно: `main.js`'s обработчик ошибки закладки деревни раньше ВСЕГДА
  говорил игроку «поверхность неровная», что было неправдой в 100% случаев
  (движок никогда не отклоняет закладку из-за рельефа — только копает/
  подсыпает глубже, см. `terrain.js`). Теперь сообщение честное
  («попробуй другое место или посмотри лог»).

### 5.7 Зацикленная телепортация жителей

Тетеринг (`startTetherLoop`, `npc.js`) мгновенно телепортировал жителя
домой при выходе за радиус — но телепорт не сбрасывал текущую цель
ванильного ИИ, так что житель на следующем тике снова шёл к той же
дальней цели → видимый бесконечный цикл "вышел → телепорт → вышел".

**Фикс:** для НЕ-старост нужно `STRIKES_BEFORE_RECALL = 3` подряд проверки
вне радиуса (~6 секунд, проверка раз в 40 тиков), прежде чем вернуть —
даёт естественному ИИ шанс вернуться самому. Счётчик (`village:overCount`
на NPC) сбрасывается при любом возврате в радиус. Староста — без
изменений, мгновенный возврат без права выйти вообще (`STRIKES` не
применяется к нему).

### 5.8 Значительная доработка мока `@minecraft/server` (важно перед новыми тестами)

`tests/node_modules/@minecraft/server/index.js` теперь умеет:
- **Симулировать незагруженные чанки**: `dim._markUnloaded({x1,x2,z1,z2})` /
  `dim._clearUnloaded()` — `getBlock`/`spawnEntity` бросают то же самое
  исключение, что настоящий движок (`LocationInUnloadedChunkError`), пока
  область помечена.
- **`dimension.runCommand(cmd)`** — записывает команды в `dim._commands`,
  ничего больше не делает (соответствует реальности: `/tickingarea add` не
  подгружает чанк мгновенно).
- **`system.runTimeout(fn, ticks)`** — по умолчанию срабатывает СРАЗУ (не
  ломает старые тесты, ожидающие синхронного результата). Для тестов,
  которым нужно контролировать момент срабатывания: `system._deferTimeouts
  = true` перед действием, затем `system.flushTimeouts()`, когда нужно
  симулировать «время прошло». См. паттерн в `bugfix_round3.mjs`.
- **`spawnEntity` бросает ошибку**, если `identifier` содержит `<` (см.
  §5.6) — соответствует реальному движку 1.21.80+.
- **`options.spawnEvent`** третьим аргументом сохраняется в
  `entity._spawnEvent` — можно проверять в тестах, что правильный API
  реально используется, а не просто «не упало».

### 5.9 Методология проверки API перед использованием (новое, из-за Round 3 регрессии)

Round 3 сломал закладку деревни целиком именно потому, что я использовал
API-паттерн (`spawnEntity` с event внутри строки идентификатора) из
документации/памяти, не сверившись с движком владельца. Это привело к
формальной методологии, обязательной для любой правки, трогающей:
- `dimension.spawnEntity` / любой другой script API метод с недавними
  breaking changes;
- Любой `minecraft:*` идентификатор блока/предмета/сущности, который не
  подтверждён УЖЕ где-то в этом кодовом дереве (т.е. новый для проекта).

**Правило:** перед использованием — свежий `web_search` +
`web_fetch` актуальной страницы `learn.microsoft.com/.../scriptapi/...`
или `learn.microsoft.com/.../vanillalistingsreference/blocks` (см. ниже)
для конкретного символа/ID, а не из training-памяти. Память может быть
устаревшей или относиться к другой версии движка — обе моих реальных
регрессии (`cobblestone_stairs`, `spawnEntity<event>`) произошли именно
так.

**Ссылки на актуальные официальные источники (по состоянию на этот
раунд):**
- `https://learn.microsoft.com/en-us/minecraft/creator/reference/content/vanillalistingsreference/blocks?view=minecraft-bedrock-stable`
  — полный официальный список ID блоков с их states. Страница отдаёт
  контент постранично при фетче (упирается в ~500 строк алфавита за раз,
  до "green\_..." в моём последнем фетче) — если нужен ID дальше по
  алфавиту, вероятно потребуется другой подход к пагинации/фетчу.
- `https://learn.microsoft.com/en-us/minecraft/creator/reference/content/vanillalistingsreference/items?view=minecraft-bedrock-stable`
  — то же самое для предметов.
- `https://learn.microsoft.com/en-us/minecraft/creator/scriptapi/minecraft/server/...` —
  актуальная документация Script API по конкретному классу/методу
  (`Dimension`, `Entity`, `System` и т.д.) — предпочтительнее сторонних
  зеркал (`jaylydev.github.io/scriptapi-docs`), которые могут архивировать
  устаревшие версии по историческим причинам (сами по себе полезны для
  СРАВНЕНИЯ версий, но не как единственный источник истины).
- `@minecraft/vanilla-data` (npm) — версионированный TypeScript-пакет с
  полными enum'ами блоков/предметов/сущностей ТОЧНО под версию движка.
  Не удалось напрямую зафетчить файлы пакета в этой сессии (ограничения
  инструмента web_fetch на новые/непосещённые URL) — если в новой сессии
  инструменты позволяют fetch с unpkg.com/npmjs.com напрямую, это
  предпочтительнее постраничного HTML-скрейпинга документации.

**Спот-проверка в этом раунде:** прогнал ~70 из 210 уникальных
`minecraft:*` идентификаторов, реально используемых в кодовой базе (все,
что алфавитно попадают в диапазон, который успел зафетчить, `a`–`green_*`),
против официального списка — **все подтверждены валидными**, кроме уже
исправленного `cobblestone_stairs` (который в официальном списке
подтверждённо отсутствует, что ещё раз доказывает правильность фикса).

**Найдено, но НЕ исправлено (не хватило прямого подтверждения):**
`minecraft:wooden_door` используется в 9 местах (`builder.js`,
`city_buildings_11_15.js`, `final_city_19_20.js`,
`special_buildings_16_18.js`, `specials.js`, `walls.js`) как дверь для
палитры "plains"/дуба по умолчанию. Официальный список показывает
консистентный паттерн `<порода>_door` для КАЖДОЙ породы дерева
(`acacia_door`, `birch_door`, `cherry_door`, `crimson_door`,
`dark_oak_door`...) без исключения для дуба — то есть современный ID,
вероятно, `minecraft:oak_door`, а `wooden_door` может быть устаревшим
алиасом (как было с `cobblestone_stairs`/`stone_stairs`). **НЕ исправлено
вслепую**, потому что: (а) не удалось зафетчить именно секцию на букву
"o"/"w" официального списка, чтобы увидеть `wooden_door` явно
отсутствующим или явно присутствующим как алиас; (б) в отличие от
`cobblestone_stairs`, нет подтверждённого сообщения об ошибке от владельца
именно про двери — то есть, возможно, `wooden_door` — рабочий legacy-алиас,
который движок молча принимает (в отличие от `cobblestone_stairs`,
которого не существует вообще). Слепое изменение рабочего кода без
подтверждения — именно тот тип риска, который привёл к Round 3 регрессии.
**Следующий шаг**: либо зафетчить недостающую часть списка и сверить
напрямую, либо (надёжнее) попросить владельца проверить в игре, действительно
ли двери домов с палитрой "plains" (равнины/дуб) появляются нормально —
если да, `wooden_door` работает и трогать не нужно.

### 5.10 Экосистема инструментов Bedrock-разработки (справочно, не подключено)

По запросу владельца исследовано, какими инструментами реально пользуются
разработчики Bedrock-аддонов (в т.ч. с ИИ-ассистентами). Ничего из этого
не подключено к проекту в этом раунде — это установленные знания на
будущее, если понадобится:

- **`@minecraft/server-gametest`** (официальный GameTest Framework) —
  единственный способ гонять автотесты ВНУТРИ настоящего движка (не мока),
  через `/gametest run`. Ловит именно те баги, что моки не ловят
  (deprecated API, unloaded chunks по-настоящему). Требует toggle "Beta
  APIs" в настройках мира и `.mcstructure` файлы под каждый тест — не
  предлагается подключать к шипящемуся аддону (эксперимент. тогглы
  нежелательны для "ванильного" мода), но может быть отдельным dev-only
  behavior pack'ом для владельца, если он захочет сам гонять smoke-тесты
  на устройстве перед тем как присылать скриншоты. Не реализовано — ни
  одного `.mcstructure`/теста в этом раунде не создано.
- **Regolith / `rgl`** — компилятор-пайплайн для аддонов (единая
  project-папка вместо ручного zip, "filters" для трансформации файлов
  при сборке). Проект сейчас использует простой ручной `zip`-скрипт (см.
  §3) — этого достаточно для текущего размера проекта; переход на
  Regolith — это смена всего workflow, не делать без явного запроса.
- **bridge. v2** — GUI-редактор с JSON-схемами/автодополнением для
  Bedrock-файлов. Инструмент для СТОРОНЫ владельца, если он когда-нибудь
  будет редактировать JSON руками вне Claude.
- **VS Code расширения**: Blockception's Minecraft Bedrock Development
  (валидация JSON/Molang), Mojang's Minecraft Bedrock Debugger
  (интеграция с дебаггером), Prettier — тоже для стороны владельца, не
  применимо к текущему Claude-based workflow напрямую.



- Только ванильные блоки/текстуры/модели.
- Алмазы и незерит никогда не производятся (шахтёр: железо/золото/редстоун/
  лазурит, весовая таблица в `production.js`).
- Не добавлять караваны, репутацию, другие биомы, уровни выше 20.
- Не менять баланс L1-15 без явного запроса владельца.
- Ванильные деревни никогда не заменяются/не трогаются (`worldgen.js`
  проверяет `hasVanillaVillageNearby`).
- L19-20 не имеют наград (`reward.kind: "none"`) — так и задумано.
- Полная зеркальная локализация RU/EN — при любой новой строке добавлять
  ключ в ОБА `.lang` файла (проверяется `localization_*.mjs`).
- Никогда не заявлять о ручном тесте на устройстве без реального
  подтверждения владельца.
- **Никогда не используй spawn-событие внутри строки идентификатора
  сущности** (`"type<event>"`) — устарело, движок бросает исключение. Всегда
  `spawnEntity(type, loc, {spawnEvent: "..."})`. Мок это теперь тоже
  проверяет (§5.8).
- **Перед использованием любого нового `minecraft:*` идентификатора или
  script API метода** — свежая проверка через `web_search`/`web_fetch`
  официальной документации (см. §5.9), не из training-памяти.
- **Перед изменением версии в manifest.json** — обнови ВСЕ вхождения разом
  (header, все modules, dependencies на UUID второго пака), см. §3.
- Перед любой сдачей — полный regression с точными цифрами, не «тесты
  прошли».

## 7. Что делать дальше (по приоритету)

1. **Дождаться подтверждения от владельца по 0.5.3.** Спроси в начале
   нового чата, тестировал ли уже. Если новые баги — та же методология:
   root cause в реальном коде → минимальный фикс → тест, доказывающий
   причинность → полный regression → аккуратная версия manifest (§3).
2. **Полный редизайн планировки деревни L1-10** — крупнейшая нерешённая
   задача, явно запрошенная владельцем (единая дорога, дома вдоль неё,
   расстояние под будущие апгрейды ремесленников). В коде уже лежит
   нетронутый, гораздо более строгий каркас именно под это
   (`spatial_plan.js`, `defences_roads.js` — жёсткие assert-границы,
   `reserveEnvelopes`, финальный радиус R94), но **намеренно не подключён**

   спланированный, но не завершённый заход). Это отдельная, немаленькая
   задача — начинать с design note (state keys, порядок миграции существующих
   L1-10 плейсментов на новый каркас, failure matrix), не с кода.
3. **"Дом посередине дорожки"** (репортнуто владельцем, не подтверждено
