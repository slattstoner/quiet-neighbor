# Постройки как структуры

Сюда кладутся `.mcstructure` — по файлу на постройку. Пока папка пуста, и это
нормально: `building_manifest.js` тоже пуст, а рантайм в этом случае строит
всё как раньше, процедурно. Ни одна постройка не пропадёт из-за того, что
конвейер уже есть, а файлов ещё нет.

## Зачем

Сегодня постройка — это функция: шестьдесят функций, в среднем по 48 строк
рукописной геометрии, плюс 188 захардкоженных координат. Это и есть потолок
того, сколько города мод вообще может вместить (у MineColonies — больше
десяти тысяч схематик, и руками столько не пишут).

Плюс два побочных выигрыша, которые важны сами по себе:

- **Незагруженные чанки перестают быть молчаливым провалом.** `setBlock` в
  незагруженном чанке просто ничего не делает — ради этого написаны
  `holdLoadedArea`, `withRetry` и весь бюджет тикающих зон. В документации
  `StructureManager.place` сказано прямо: *«Structures placed in unloaded
  chunks will be queued for loading»*.
- **Один вызов движка вместо нескольких сотен** — прямая экономия против
  сторожа в 3000 мс.

## Как добавить постройку

1. Построй её в игре (проще всего — в креативе, на плоском мире).
2. Материалы, которые должны меняться по биому, выложи **блоками-маркерами**
   вместо настоящих. Список — в `PLACEHOLDER_BLOCKS` в
   `building_manifest.js`:

   | Маркер | Во что превратится |
   |---|---|
   | `purple_terracotta` | стена (доски палитры) |
   | `red_wool` | фундамент (камень палитры) |
   | `white_wool` | крыша (ступени палитры) |
   | `copper_block` | брус (бревно палитры) |
   | `quartz_block` | акцент |

   Маркеры выбраны так, что ни один из них не встречается в настоящей
   деревне, — поэтому замена по id блока не может съесть то, что должно было
   остаться.

3. Выдели постройку структурным блоком и нажми Export. Файл положи как
   `structures/gv/buildings/<имя>.mcstructure`.

   Namespace берётся из **первой подпапки**: `structures/gv/buildings/x.mcstructure`
   даёт идентификатор `gv:buildings/x`. Файл, лежащий прямо в `structures/`,
   получает namespace `mystructure` — так делать не надо.

4. Допиши запись в `BUILDING_MANIFEST` (`building_manifest.js`). Форма записи
   и пример — в комментарии над самим массивом.

Ограничение движка: структура не может быть больше **64×384×64**.
`defineBuilding()` это проверяет и отказывается принимать запись, под которую
файла всё равно не могло бы существовать. Поэтому стены и дороги остаются
процедурными — зданиями становятся здания.

## Ориентация: два места, которые надо подтвердить на устройстве

Обе вещи выведены из кода, а не угаданы, и обе закреплены тестом
(`tests/structure_pipeline.mjs`) — но мок их проверить не может:

- **Угол установки.** `place()` принимает одну точку, и мы считаем, что это
  минимальный угол структуры (как у структурного блока). Если на устройстве
  окажется иначе — правится только `worldAnchorFor`.
- **Поворот.** `FACING_ROTATION` в `structure_build.js`: там же выкладка, из
  которой он получен. Если постройка встанет боком — правится одна таблица.

Отдельно: на facing 2 и 3 структура встаёт **зеркально**. Это свойство самого
`toWorld` (`(f,s) → (s,f)` — отражение, а не поворот), оно вшито во все
существующие билдеры. Для дома это косметика, а участок всё равно совпадает,
потому что угол считается по преобразованным углам, а не по facing напрямую.
Если ориентация где-то принципиальна — это POI, а не часть структуры.

## Как не строить шестьдесят домов руками

`captureBuilding()` в `structure_build.js` снимает уже стоящую постройку в
структуру (`createFromWorld` + сохранение в мир). То есть процедурный билдер,
который дом уже умеет рисовать, рисует его — а потом структурный блок
экспортирует результат в файл. Это dev-утилита, в шипящемся рантайме её
никто не вызывает.
